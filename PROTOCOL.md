# Протокол Slinex SL-10PT (Gooclient/Goolink "Mobile Eye Door") — OWSP

Результаты реверс-инжиниринга `com.gooclient.mobileeyedoor.plus.apk`.
Домофон **не использует RTSP/ONVIF** — только проприетарный протокол **OWSP**
(Over-Wire Streaming Protocol, пакеты TLV поверх TCP или UDT).

## Общее

- Транспорт: **TCP** (в LAN — «INTMODE», прямой коннект; через интернет — UDT/P2P/relay Goolink).
- Порт по умолчанию: **100** (fallback в приложении, если поле порта пустое; фактически используется порт, введённый пользователем / полученный при поиске).
- Видео: **H.264 Annex-B** (кадр = последовательность NAL-юнитов с start-кодами).
- Аудио: **G.711 A-law** (`waveFormat = 31257`), 8000 Гц, моно (также поддерживаются G.726 / Speex / G.711 µ-law).
- Приложение почему не работает на новых Android: нативные библиотеки только `armeabi` (32-bit ARMv5/6), которых нет на 64-битных устройствах.

## Формат кадра OWSP (TCP-поток)

```
Смещение  Размер  Поле
0          4       packet_length  u32 BIG-endian  = 4 + Σ(4 + tlv_len) по всем TLV
4          4       packet_seq     u32 LITTLE-endian (счётчик, с 1)
8          ...     TLV-записи:
                     u16 LITTLE-endian tlv_type
                     u16 LITTLE-endian tlv_len
                     byte[tlv_len]  value (структуры little-endian)
```

Полный размер пакета в потоке = `8 + (packet_length - 4)` = `packet_length + 4`.
Ограничение на packet_length в клиенте: `0 < packet_length <= 196605 (0x30005)`.

Важно: **TLV len — u16**, поэтому у больших I-кадров (>65535 байт) поле len
заполнено некорректно, и клиент вычисляет реальную длину:
`if (packet_length - tlv_len > 24) tlv_len = packet_length - 24`
(24 = 4 + TLV99(4+12) + заголовок TLV100).

## Типы TLV (основные)

| Type | Название | Направление |
|------|----------|-------------|
| 40 | VERSION_INFO req (major, minor: u16 LE) | client → dev |
| 39 | VERSION_INFO rsp | dev → client |
| 41 | LOGIN_REQ | client → dev |
| 42 | LOGIN_RSP (`result` u16 LE: 1=OK, 2=неверный пароль, 5=макс. пользователей, …) | dev → client |
| 49 | KEEP_ALIVE req (len 0) | client → dev |
| 44/45 | STREAM_DATA req/rsp | (в этой версии приложения не используется) |
| 98 | AUDIO_DATA (сырой G.711a) | dev → client |
| 99 | VIDEO_FRAME_INFO (12 байт, см. ниже) | dev → client |
| 100 | VIDEO_IFRAME_DATA (H.264 Annex-B) | dev → client |
| 101 | VIDEO_PFRAME_DATA (H.264 Annex-B) | dev → client |
| 199/200/203 | STREAM_FORMAT_INFO (40 байт, см. ниже) | dev → client |
| 331/332 | TALK req/rsp (двусторонняя аудиосвязь) | |
| 352 | ADD_CHANNEL_STREAM req | |
| 425/426 | LOCK req/rsp (открытие замка) | |
| 465/466 | DEVICE_RESTART req/rsp (перезагрузка, payload 4 байта нулей) | client → dev |
| 469 | DEVICE_SERVER_SET req (push/md/email, delaytime) | client → dev |
| 70 | DVS/DHCP info push от устройства | dev → client |

## Логин (протокол >= 5.0) — `TLV 40 (v5.0) + TLV 41 (LoginRequestEx, 68 байт)`

Поля выверены по референсному дампу рабочей сессии приложения (35+ секунд
непрерывного стрима, `slinex.pcap`) — побайтово:

```
packet_seq    u32 LE = 0        (!) первый пакет соединения
encryptType   u8    = 0
userName      byte[32]  (ascii, дополнен нулями, НЕ шифруется)
password      byte[16]  (см. шифрование ниже)
deviceId      u32 LE = 0        (!) не 1
flag          u32 LE = 0        (!) не 2 — «flag=2» в прошивке STM83xx
                                  означает превью-режим и сессия убивается
                                  через ~2 с
reserve3      byte[3] = 0
channelMask   u32 LE = 1 << (channel-1)
streamMode    u8    = 1 (sub)   (!) приложение всегда запрашивает суб-поток
dataType      u8    = 2 (mixed = video+audio)
reserve       u8 = 0
reserve2      u8 = 0
```

## Логин (старые прошивки < 5.0) — `TLV 40 (v3.7) + TLV 41 (LoginRequest, 56 байт)`

```
userName      byte[32]
password      byte[16]
deviceId      u32 LE = 0
flag          u8 = 0
channel       u8 = 0 (первый канал, 0-based)
reserve       byte[2]
```

Автоконфликт версий как в приложении: сначала отправляется «новый» логин
(v5.0); если в ответе версия < 5.0 — переподключение со «старым» логином.
Важно: **STM83xx отвечает на версию ЭХОМ TLV 40** (не TLV 39, как в SDK!),
поэтому отклик версии надо искать среди TLV 39 и 40.

### Шифрование пароля

`enc[i] = pwd[i] ^ ((key[i mod 6] + 25) & 0xFF)`, где `key = "lbtech"`.
Шифруются только первые `len(pwd)` байт, остальное — нули.

Тест-векторы: `"888888"` → `BD 43 B5 46 44 B9 00 …`,
`"123456"` → `B4 49 BE 4A 49 B7 00 …` (16 байт).

## После логина — НИЧЕГО не отправлять!

**Главное открытие референсного дампа: после логина клиент не отправляет
НИ ОДНОГО пакета** — ни keep-alive, ни подтверждений аудио, ни запросов.
Сессия живёт 35+ секунд (пока пользователь не закрыл просмотр) на чистом
TCP-приёме. Все прежние теории о flow-control оказались неверными:

- keep-alive TLV 49 — **не нужен** (остался опцией `--keepalive`);
- аудио-ACK TLV 97 — **не нужен** (остался опцией `--audio-ack`);
- TLV 427 (вкл. аудиотракта) — **не отправляется приложением**
  (остался опцией `--tlv427`); приём звука в приложении — локальный флаг
  `EyeProtocolParser.setAudio()`, гейтующий доставку TLV 98 в AudioTrack;
- TLV 44 (StreamDataRequest) — не используется.

Устройство после логина шлёт: `TLV 40 (эхо версии) + TLV 70 (DVS info) +
TLV 42 (result=1) + TLV 203 (формат)`, затем поток: видео `TLV 99+100/101`,
аудио `TLV 97+98` (320 байт G.711 на чанк, идут всплесками — на панели
очевидно есть VAD; таймстамп TLV 97 — счётчик сэмплов 8 кГц).

## Реальная сессия (из референсного дампа, 35 с)

- Разрешение 320x240@5fps (заявлено), фактически кадры идут ~1/с
  (frameIndex в TLV 99 прыгает по 3-6).
- I-кадры: 3 штуки за 35 с (интервалы 7-20 с, нерегулярно).
- Аудио: 385 чанков × 320 байт ≈ 4 с звука всплесками (VAD на панели).
- Приложение перед логином открывало 3-4 «пустых» TCP-соединения
  (connect → пара ACK → close, 0 байт данных) — пробы/ретраи.
- В дампе каждый пакет встречался трижды (захват с 3 интерфейсов) —
  при анализе дедуплицировать по tcp.seq.

## Наблюдения с боевого дежурства (инциденты 27–28.10, полный разбор)

**Устройство перезагружается ЕЖЕДНЕВНО ~06:50** (27.10 в 06:52, 28.10 в
06:49 — ровно сутки; видимо, штатный watchdog/расписание прошивки). Сессии
до перезагрузки живут стабильно: 21.2 ч / 228533 кадра на каждом канале.

Хронология после перезагрузки (по логу шлюза):

1. **+0 с**: все 4 OWSP-сессии закрыты одновременно чистым FIN.
2. **~2 мин**: `Connection refused` — устройство грузится.
3. **~2–4 мин**: TCP принимается, версия отвечает (TLV 40, 5.0), но логин
   отклоняется **кодом 2** на все каналы — база пользователей ещё не
   загружена. Это НЕ смена пароля — ждать загрузки конфига.
4. Далее логины принимаются; шлюз поднимается сам (backoff 3→60 с).

### Баг клиента, найденный по логу 28.10 (исправлен)

Симптомы: канал 3 — работает; канал 2 — логин OK, но 15 с тишины, цикл
реконнектов; канал 4 — бесконечный «мусор протокола», картинка
рассыпается; каналы 1–2 под конец — код 5 (лимит подключений).

Причина — **гонка в `_login`**: цикл чтения выходил по первому полученному
полю (эху версии), не дождавшись кода ответа логина. После перезагрузки
устройство отвечает медленно, версия и код приходят разными TCP-сегментами
→ клиент отправлял **второй (старый) логин в тот же сокет**. Прошивка уже
подняла сессию по первому логину; второй ломал её состояние: сессия
жила, но данными не отвечала (канал 2) либо слала поток с битым
фреймингом (канал 4). Кроме того, буфер чтения обнулялся между попытками —
полупринятый пакет терялся, поток начинался с середины кадра. Следы гонки
в логе: строки «логин отклонён, код=2 (вариант старый)» без парной
«(вариант новый)».

Вторая проблема — **восстановление после мусора**: дроп всего буфера
(стиль ParserStateErrDate) не возвращает выравнивание: TCP не сохраняет
границы пакетов, следующий recv начинается с середины кадра → каскад
десинка. Наблюдалось: канал 4 отбрасывал ВЕСЬ поток (~22 КБ за GOP),
изредка ловя выравнивание случайно → артефакты.

Исправления:

- `_login`: в одном соединении — ровно один логин; ответа логина ждём
  до конца (выход только по result/дедлайну). Второй вариант логина —
  только на СВЕЖЕМ сокете. Прежний вариант — `_login_attempt`/`_login`.
- Парсер: ресинк по маркеру **TLV 99** (`63 00 0C 00` — VideoFrameInfo,
  начинает каждый видеокадр): ищем маркер, проверяем правдоподобность
  поля length пакета перед ним, продолжаем разбор с границы кадра
  (`resync_owsp`).
- Backoff: сессия **без единого кадра** («тишина» после логина) считается
  неудачей — иначе цикл «логин→15 с тишины→реконнект» каждые 18 с
  протекает соединениями на устройстве и приводит к коду 5.
- Рекомендация: на период наблюдений держать включённым `--dump FILE` —
  строка DESYNC печатает первые 64 байта мусора в hex.

### Код 2 после перезагрузки (27.10, доп. наблюдение)

27.10 после загрузки конфига канал 1 (channelMask=0x01) упорно
отвергался кодом 2 ещё 2.5+ ч при живых 2–4. 28.10 этой аномалии НЕ

## Отказоустойчивость парсера (ParserStateErrDate)

При невалидном `packet_length` в начале буфера приложение (класс
`EyeProtocolParser`) не рвёт сессию: оно отбрасывает данные до конца
буфера (`setNewPosRead(rawWriteIndex)`, состояние `ParserStateErrDate`)
и продолжает. Шлюз делает так же: мусор логируется и пропускается,
сессия живёт.

## Двустороннее аудио / громкая связь (talk) — реализовано

Путь в приложении: кнопка «говорить» → `EyeSourceTransNet.setTalk` →
`TalkRequestReqPack` (TLV 331) → ответ TLV 332 → поток `writeTalkData`
(микрофон → `AudioInfoRequestPack`). Весь обмен идёт в РАБОТАЮЩУЮ
стрим-сессию (как замок TLV 425).

### TLV 331 — TalkRequest (8 байт, TLV_V_TalkRequest)

| поле | размер | значение |
|------|--------|----------|
| deviceId | u32 LE | 0 |
| action | u8 | 1 = старт, 2 = стоп |
| chn | u8 | **1-BASED** (`setTalk: chanIndex+1`) |
| reserve | 2 | нули |

(Остальные параметры упаковщика — samplesPerSecond и пр. — в пакет
НЕ пишутся, тело всегда 8 байт.)

### TLV 332 — TalkResponse (24 байта, раскладка по ЖЕЛЕЗУ)

Подтверждено дампом с панели 31.10 15:31 — hex
`01000000401f000000300000257a0100e803100019000000`:

| поле | offset | значение на железе |
|------|--------|----------|
| result | 0 | u16: 1 = успех; **23 = «talk занят»** (наблюдение 15:21: после 332, потерянной в мусоре протокола, панель держала talk канала открытым и отказывала другому каналу) |
| reserve | 2 | u16, 0 |
| samplesPerSecond | 4 | u32, 8000 |
| audiobitrate | 8 | u32, 12288 (0x3000 — семантика мутная) |
| waveFormat | 12 | u16, 31269 (0x7A25, G.711 µ-law) |
| channelNumber | 14 | u16, 1 |
| blockAlign | 16 | u16, 1000 |
| bitsPerSample | 18 | u16, 16 |
| frameInterval | 20 | u16, 25 (мс — но наш пейсер 320 Б/40 мс работает) |

Реальные 8000 Гц (0x1F40) и waveFormat 0x7A25 лежат со сдвигом **+2 Б**
относительно `TLV_V_TalkResponse.deserialize` из APK — после result
идёт reserve u16 (первые версии парсера читали мусор «524288000 Гц»).
Панель отвечает 332 и на action=1, и на action=2. Приложение на
result=1 стартует запись микрофона.

### Поток вверх (AudioInfoRequestPack)

Один OWSP-пакет на чанк 320 Б µ-law (40 мс @ 8 кГц), темп задаёт
блокирующее чтение `AudioRecord.read(320)`:
- TLV 97 (8 Б): channelId u8 **1-based**, reserve=0, checksum u16=0,
  **time u32=200 — константа, не таймстамп**;
- TLV 98: сэмплы µ-law.

Эхо-защита приложения: `calc1` — каждый linear-сэмпл `>>2` (−12 дБ)
перед кодированием. У шлюза: `--talk-gain-shift N` (>0 тише, <0 громче,
0 — без изменений; таблица энкодера — точная инверсия декодера).

### В шлюзе

- **TalkSession** (Gateway): автостарт по первому аудио-пакету ингресса
  (331/332), автостоп через 2 с тишины ингресса (перевзводится; часы —
  от последнего feed(), а не прихода в очередь пейсера), stop() ингресса —
  флаш остатка + 331 action=2. Пейсер: ≤1 чанк 320 Б / 40 мс, готовые
  OWSP-пакеты в `_send_q` (цикл сессии — единственный писатель).
  **Backpressure**: если несент-аудио > 2 с (WATERMARK 16384 Б), feed()
  ингресса ЖДЁТ пейсера, а не выбрасывает старое (баг 31.10 14:31:
  файловый POST быстрее реального времени — «кап с выбросом» доиграл
  16960 из 40000 Б; теперь POST файла занимает время его звучания и
  доигрывается целиком). **Эксклюзив на канал** — второй ингресс
  получает «занято».
- **Ингресс A — RTSP** (ffmpeg `-f rtsp -rtsp_transport tcp`):
  ANNOUNCE (SDP m=audio PCMU/8000 — иначе 415) → SETUP (interleaved
  или UDP, mode=record) → RECORD → interleaved-RTP (`$`-кадры) →
  разбор RTP (CC/extension) → PCMU-payload в пейсер. Канал из URL:
  `rtsp://host:8554/cameraN/talk`.
  Пример: `ffmpeg -f avfoundation -i :0 -acodec pcm_mulaw -ar 8000
  -ac 1 -f rtsp -rtsp_transport tcp rtsp://host:8554/camera/talk`
- **Ингресс B — HTTP**: `POST /talk?ch=1`, тело — сырой µ-law 8 кГц
  (Content-Length или chunked): `curl -X POST --data-binary @x.ulaw
  -H 'Content-Type: audio/basic' http://host:8555/talk?ch=1` →
  JSON {ok, bytes, sent, duration_s}. Занятость → 409.
- **Ингресс C — RTSP backchannel** (go2rtc / ONVIF Profile T, как
  Dahua/Hikvision): DESCRIBE выдаёт третий трек **trackID=2
  `m=audio PCMU/8000` + `a=sendonly`**; треки воспроизведения —
  `a=recvonly`. **Направления в SDP источника — С ТОЧКИ ЗРЕНИЯ
  КЛИЕНТА** (не RFC-буквально «сторона сервера»): `a=recvonly` =
  «клиент принимает» (воспроизведение), `a=sendonly` = «клиент шлёт»
  (backchannel) — так пишут реальные камеры (проверено по тестам
  go2rtc: TestBugSDP7 #1426, Hikvision; без атрибута go2rtc тоже
  считает recvonly). Инверсия 31.10 давала probe «streams: EOF» и
  409. go2rtc шлёт микрофон SETUP-ом sendonly-трека БЕЗ mode=record
  и БЕЗ RECORD (наш RECORD оставлен для совместимости). При нажатии
  микрофона go2rtc РЕКОННЕКТИТ продюсер: SETUP видео+аудио+talk на
  свежем соединении, PLAY → mic-RTP interleaved на канале трека.
  **TalkSession ЛЕНИВАЯ**: SETUP трека НЕ занимает канал (go2rtc
  держит backchannel открытой всю сессию просмотра), сессию панели
  открывает первый RTP; 2 с тишины — слот освобождается (autorelease),
  следующий RTP откроет заново.
- Кодек только PCMU (µ-law) 8 кГц моно — как тракт панели.
- События `talk` start/end/error → лог + /events + MQTT;
  /status содержит `"talk"` (bytes_in/bytes_sent/ошибка).
- **На железе ПОДТВЕРЖДЕНО 31.10**: обе аудио-панели (каналы 1 и 2)
  ответили TLV 332 result=1 на 331, сессии живы; **go2rtc two-way
  audio работает** (микрофон браузера: сессии 16–55 с, autorelease
  после 2 с тишины); HTTP-тон 40000/40000 Б доигрывается целиком
  (~5 с). При провале старта (таймаут 332 / result≠1) шлюз шлёт
  331 action=2 — очистка состояния панели (урок 15:21).

## История: «лимит сессии ~2 секунды» (решено)

Первые версии шлюза жили с симптомом: прошивка STM83xx рвала соединение
через ~2.0–2.7 с (RST, 5–10 кадров). Тогда причину искали в отсутствии
flow-control (keep-alive TLV 49, аудио-ACK TLV 97, TLV 427, TLV 44) —
ничего не помогло, и даже был сделан обход «бесшовной ротацией».

**Референсный дамп (slinex.pcap) показал настоящую причину: неверные
поля логина.** Мы отправляли `packet_seq=1, deviceId=1, flag=2,
streamMode=0` — а рабочее приложение `0, 0, 0, streamMode=1`. Судя по
поведению, `flag=2` включает в прошивке STM83xx превью-режим: устройство
отдаёт один-два GOP и закрывает соединение. С правильным логином сессия
живёт неограниченно без единого клиентского пакета.

Аудит APK подтвердил и отсутствие «ответа» для видео:
`EyeSourceTransNet.OnVideoFrameInfo()` (TLV 99) лишь обновляет локальные
переменные, `OnStreamFormatInfo()` (TLV 203) инициализирует декодер,
`TLV_T_MOBILE_INFO_REQ = 72` — мёртвая константа.

**Бесшовная ротация** (`--rotate`) была страховкой для проблемных прошивок:
фоновый поток заранее готовил замену соединения и грел его до I-кадра.
После фикса логина сессии живут сутками — ротация УДАЛЕНА из шлюза
(31.10.2026) вместе с режимом «прогрева» `media=False` в обработчике TLV.

## Реальное устройство (STM83xx, Slinex)

- Порт OWSP сообщается при поиске в LAN (в нашем случае 10510), а не «классические» 100.
- `TLV 70`: name=`STM83xx`, 4 канала; формат 320x240@5fps; аудио G.711 **µ-law**
  (`wave=0x7A25`) — в RTSP маппится как PCMU (PT 0).
- 4 канала одновременно: отдельное соединение на канал, логин маской этого канала.
- **Main/sub поток (проверено 31.10)**: `streamMode` логина — и есть селектор
  (`OWSP_StreamType`: MAIN=0, SUB=1, VOD=2, SETTING=3). `--main`
  (streamMode=0) прошивка принимает БЕЗ обрыва — ранние разрывы «через ~2 с»
  были виной неверных полей логина (deviceId=1, flag=2), а не потока. Но
  формат НЕ меняется: 320x240@5fps и на main, и на sub — у панели один
  режим энкодера, платформенная фича dual-stream на этом железе не
  наполнена. Приложение выбирает main/sub по биту 0 поля `deviceType`
  из TLV 70 (offset 70: `(type & 1)==1 → MAIN, ==0 → SUB`);
  TLV 44 StreamDataRequest — `[videoChannel, audioChannel, reserve u16]`,
  включение каналов данных, НЕ селектор качества.

### Поддержка клиентских TLV прошивкой (проверено на железе 31.10)

| TLV | Команда | Сессия | Результат |
|-----|---------|--------|-----------|
| 425 (замок) | LockRequest | стрим | **работает** (426 result=1; канал 1-based — подтверждено на железе 31.10 12:35) |
| 331 (talk) | TalkRequest | стрим | **работает** (332 result=1, обе аудио-панели — каналы 1 и 2 — подтверждено 31.10 14:31) |
| 1054 (громкость) | VolumeConfigRequest | стрим | **разрыв соединения** без ответа |
| 1007 (время) | TimeSyncRequest | стрим и settings (dt=0 и dt=2) | **разрыв соединения** без ответа — оба пути APK проверены |
| 465 (ребут) | DeviceRestartRequest | settings | **разрыв соединения** без ответа |

Паттерн: неизвестный прошивке клиентский TLV → разрыв соединения.
Settings-экран приложения («параметры устройства») на этой панели не
работает — весь класс settings-команд прошивкой не поддерживается.
Подтверждённые команды — замок (425) и talk (331), только в
стрим-сессии.

### TLV 99 — VIDEO_FRAME_INFO (12 байт)

```
channelId  u8
reserve    u8
checksum   u16 LE
frameIndex u32 LE
time       u32 LE   (метка времени, мс)
```

Кадр видео приходит пакетом `TLV 99 + TLV 100/101`; данные TLV 100/101 — готовый
H.264 Annex-B кадр (I-кадр начинается с SPS/PPS/IDR).

### TLV 203 — STREAM_FORMAT_INFO (40 байт, всё LE)

```
videoChannel u8, audioChannel u8, dataType u8, reserve u8,
codecId u32, videobitrate u32, width u16, height u16,
framerate u8, colorDepth u8, videoframeInterval u8, videoreserve u8,
samplesPerSecond u32, audiobitrate u32, waveFormat u16,
channelNumber u16, blockAlign u16, bitsPerSample u16,
audioframeInterval u16, audioreserve u16
```

`waveFormat`: 31257 (0x7A19) = G.711 A-law, 31269 (0x7A25) = G.711 µ-law, 31264 = G.726, 31267 = Speex.

## Мультика­мерность (несколько панелей/камер)

- **Модель системы (по железу, 31.10): каналы STM83xx — ВЫЗЫВНЫЕ ПАНЕЛИ**
  (дверные станции), а не 4 сессии одного устройства: динамики и
  микрофоны находятся в панелях (на этой инсталляции аудио-панели —
  каналы 1 и 2), у каждой панели свой замок. Поэтому канал в
  talk (TLV 331 chn) и замке (TLV 425 channel) выбирает ПАНЕЛЬ.
- **Модель приложения: одно TCP-соединение на канал.** `SourceIdentNet.isSameIdent()`
  сравнивает record + `chanIndex` (канал), а `EyeNetMgr.socketRequest()` всегда создаёт
  новый сокет; 4-экранный обзор (`AllViewSet`) = 4 `EyeVideoView` = 4 соединения,
  каждое логинится маской своего канала.
- **Логин (≥5.0):** `channelMask` (u32 LE) — битовая маска каналов:
  `1 << (channel-1)`; канал 1 → `0x01`, каналы 1–4 → `0x0F`.
- **Логин (<5.0):** одиночный байт `channel` (0-based) — один канал на соединение.
- Каждый кадр помечается каналом: TLV 99 (`VIDEO_FRAME_INFO`) начинается
  с `channelId` u8.
- **TLV 352 `AddChannelStreamRequest`** (6 байт): `channelMask` u32 LE +
  `dataType` u8 + `reserve` u8 — добавление каналов в уже работающий поток
  (в этом билде приложения UI-ем не используется, но протоколом поддерживается).
- **TLV 64 `SwitchChannelRequest`** (`sourceChannel`, `destChannel`; новые прошивки —
  1-based) и **TLV 350** (групповое переключение, маски) — смена канала «на лету».
- **TLV 70 `DeviceInfo`** (72 байта, пушится устройством): `companyIdentity[16]`,
  `equipmentIdentity[16]`, `equipmentName[16]`, `equipmentVersion[16]`,
  `year` u16 LE, `month` u8, `day` u8, **`channleNumber` u8 (offset 68)**,
  `alarmType` u8, `deviceType` u8, `reserve` u8 — число каналов устройства.
- Лимит одновременных подключений: код ошибки 5 (`_RESPONSECODE_MAX_USER_ERROR`,
  обычно ~4–5 «пользователей»). При 4 каналах шлюз занимает 4 слота — учитывайте
  параллельное использование мобильного приложения.

## Поиск устройств в LAN (опционально)

UDP: multicast `235.10.10.10:1500` и broadcast `255.255.255.255:1500`,
запрос `_GooPacketHeader{msgType=40967 (0xA007) LE u16, msgLength=32 LE u16} + deviceId[32]="0"`.
Ответ `msgType=40968`: `deviceId[32]`, `type u16 LE`, `bindport u16 LE`, `addr[32]`.
`bindport` — TCP-порт для OWSP.

## Удалённая перезагрузка устройства (TLV 465) — реализовано в шлюзе

Путь кнопки «Перезагрузить» в настройках приложения
(`DeviceRemoteSettingActivity` → `com.goolink.comm.DeviceConfig` —
именно DeviceConfig, не CopyOfDeviceConfig →
`EyeProtocolPacker.createRebootCommandRequestPacket`):

1. Отдельное TCP-соединение в тот же OWSP-порт.
2. Логин-настройка: `TLV 40 (v5.0) + TLV 41 (LoginRequestEx)`,
   **streamMode=3 (OWSP_MODE_SETTING)**, dataType=0, channelMask=1,
   flag=2, packet_seq=2. deviceId приложение парсит из UID устройства
   (разделитель "|"); при UID без "|" — дефолт 1. У STM83xx рабочий
   стрим-логин проходит с deviceId=0 — вероятно, команда, адресованная
   «чужому» deviceId, игнорируется.
3. Дождаться TLV 42 (result=1).
4. **НЕМЕДЛЕННО** отправить `TLV 465 DeviceRestartRequest` (4 байта
   нулей, packet_seq=1 — пакет собирается до логина).
   Без keep-alive и пауз: `OnLoginResponse → sendConfig()` пишет команду
   сразу (метод `sendAlive` с паузами 3 с в DeviceConfig — мёртвый
   код, не вызывается).
5. Устройство отвечает `TLV 466 DeviceRestartResponse` и уходит в ребут
   (может просто оборвать соединение — тоже успех).

Payload TLV 466 по десериализатору приложения — 4 байта (`reserve`).

В шлюзе: `python3 slinex_rtsp.py --host <ip> --port <port> --user admin
--password <pwd> --reboot` — one-shot; перебирает варианты полей логина
(deviceId, flag): (0,2) → (1,2) → (0,0), каждый на свежем соединении,
пока не получит 466. Параметры: `--reboot-device-id N` / `--reboot-flag
N` (конкретный вариант или семейство), `--reboot-pause SEC` (по
умолчанию 5 — пауза между вариантами: слот только что закрытой
settings-сессии освобождается прошивкой НЕ мгновенно, без паузы
следующий логин ловит код 5 и вариант фактически не проверяется —
наблюдение 28.10 на варианте (1,2)), `--reboot-retries N` (повторов
при коде 5, по умолчанию 2). Коды выхода: 0 — подтверждено 466,
2 — логин отклонён, 3 — 465 игнорируется, 4 — сеть.

**Статус на реальном железе (28.10):** НЕ РАБОТАЕТ. Проверены все
разумные варианты полей (deviceId/flag: (0,2), (1,2), (0,0)), 465
немедленно после логина, seq побайтово как в приложении — прошивка
принимает логин-настройку, а на TLV 465 закрывает соединение без 466.
Вывод: клон STM83xx команду 465 не реализует (кнопка «Перезагрузить»
в приложении на этом устройстве тоже не работает бы). Других
reboot-команд в протоколе НЕТ — весь список TLV сверён с Command.java
(TLV 311 System = язык/формат даты/имя, без флага перезагрузки).

Альтернативы удалённого ребута: служебные порты (telnet/ssh/adb/web —
 см. scan_device.py), PoE-коммутатор с управлением питанием порта, либо
 штатный ежедневный ребут ~06:50.

## Открытие замка (TLV 425/426) — реализовано в шлюзе

Путь в приложении: MainActivity (кнопка замка, case 1) → `EyeVideoView.remoteLock`
→ `EyeSourceMgr.remoteLock` → `EyeSourceTransNet.remoteLock` →
`EyeProtocolPacker.createLockPacket`. Ключевое: команда отправляется в
**РАБОТАЮЩУЮ стрим-сессию** (TransStateRun), а не в отдельное
settings-соединение — не как перезагрузка.

### TLV 425 — LockRequest (40 байт)

| поле | размер | значение |
|------|--------|----------|
| deviceId | u32 LE | 0 (хардкод `createLockPacket`) |
| lockPwd | 32 | XOR «lbtech»+25, шифруются ТОЛЬКО байты пароля (Encrypt.EncrypKey: цикл `for i < len`), остаток нули |
| channel | u8 | **1-BASED для нового протокола** (прошивка 5.0): `remoteLock` делает `if (Version == 0 \|\| Version == 1) channel++`, где newVersion=1, oldVersion=2, chanIndex сессии 0-based → для канала 1 в проводе байт 1. НАБЛЮДЕНИЕ 31.10: с 0-based прошивка отвечает 426 result=2 при ЛЮБОМ пароле; приложение при этом успешно открывает замок тем же паролем логина |
| action | u8 | 1 = открыть, 0 = закрыть |
| delayTime | u8 | удержание реле, секунды |
| reserve | u8 | 0 |

Пароль замка: если на панели задан отдельный код — он; иначе пароль
устройства (приложение: `lockable==0` → сохранённый lockPwd или
`device.getPassword()`).

### TLV 426 — LockResponse (4 байта)

`result` u16 LE (1 = успех, иначе коды _RESPONSECODE_*), `reserve` u16.
Приложение: `EyeProtocolParser` case 426 → `OnLockResponse` →
`OnUnLockResponse(boolean)`.

### В шлюзе

- `--unlock` one-shot: `./slinex_rtsp.py --host <ip> --user admin --password
  <pwd> --unlock` (+ `--lock-password`, `--lock-delay` с (default 1),
  `--lock-action` 1=открыть/0=закрыть). Поднимает стрим-сессию, ждёт
  I-кадр, шлёт 425, ждёт 426. Коды: 0 — успех, 1 — нет подключения,
  2 — отказ/нет ответа.
- HTTP-контроль работающего шлюза (`--http-port`, default 8555):
  `POST /unlock?ch=1&action=1&delay=1[&pwd=...]` → `{"ok": true, ...}`
  (502 при отказе); `GET /status` — состояние каналов; `GET /events` —
  последние события (замок, неизвестные TLV). Команда уходит через
  очередь в поток существующей сессии канала (boot-каналы уже держат
  соединения — доп. слот у устройства НЕ занимается).
- Подтверждено на моке (itest7): структура 425 совпадает побайтово с
  createLockPacket (включая 1-based канал). **На железе 31.10:**
  с 0-based каналом — `426 result=2` на любой пароль (верный/неверный/пустой),
  HTTP и MQTT пути при этом работали (событие unlock, отказ честно виден);
  после фикса на 1-based ждём щелчка реле. Приложение открывает замок
  паролем логина → пароль замка = пароль логина (lockable-диалог не нужен).

## События вызова (звонок с панели) — ring-детектор по аудио, реализовано

В OWSP-протоколе **TLV «звонок» не существует** — сверен весь список
Command.java и диспетчер EyeProtocolParser (case 35/39/40/42/45/52/65/
67/70/71/97/98/99/100/101/199/200/203/312/332/334/335/337/351/353/354/
402/404/406/408/410/412/414/416/418/420/422/424/426/428/430/1006).

Приложение получало вызовы через **вендорное облако**: push-сервер
`mobileeyedoor.push2u.com` (регистрация: `/pa.php` auth, `/pi.php` info,
`/pd.php` привязка устройства, всё RC4 «videopush2012» + base64) и MQTT-
брокер `:1883` (PushService, client `GoMDP/<phoneId>`). Устройство само
ходит в облако (у пользователя push раньше приходил — прошивка это
умеет). **Облако умерло**: DNS жив (62.210.122.90), порт 1883 закрыт —
отсюда «push перестал приходить». MQTT-путь отпадает.

### Доказано дампами (tyk.pcap — звонок, nop.pcap — фон)

При нажатии кнопки панели (все 4 OWSP-канала слушались одновременно):
- UDP-пакетов НЕТ вообще (только 4 ARP) — udp_monitor молчит правильно;
- TLV в стрим-сессиях только медиа (97/98/99/100/101), «ring»-TLV нет;
- новых TCP-соединений нет, I-frame burst нет.

Единственный след звонка — **рингтон в G.711-аудио**: панель играет
гудок на собственный динамик, микрофон панели его слышит. Характер:
- тон варблирует ~400–600 Гц (не фиксированная частота!);
- +18..+55 дБ над фоном по мощности; фон без звонка плоский (±1 дБ);
- каналы 1 и 4 — живые микрофоны (аудио идентично, один источник),
  каналы 2 и 3 — мёртвые (поток 0xFF).

Важно: тихий фон после µ-law-квантования «тонален» (R до 17) —
тональность сама по себе не дискриминатор; главный признак — МОЩНОСТЬ.

### Реализация: RingDetector (slinex_rtsp.py)

Окно 100 мс (800 сэмплов @ 8 кГц): декод µ-law (таблица CCITT G.711) →
вычет среднего → мощность P. Базлайн — EMA тихих окон (snap вниз при
P < базлайна/100 — напр. старт шлюза посреди звонка). Если
`P > базлайн × 10^(gain_db/10)` — Goertzel по сетке 300–2600 Гц (шаг
50): f0 и тональность R = P(f0)/P_total. Окно «тоновое» если R ≥ 8
(реальный гудок 10–200+, белый шум max ~7, речь <1). Старт = 3
тоновых окна подряд (300 мс), конец = 1 с нетоновых. Схема не
привязана к частоте (любой чистый тон в сетке) и к последовательности
звуков.

События `ring start/end` (каналы, freq, gain_db, duration_s) → лог,
`GET /events`, MQTT. Дедупликация по каналам в Gateway (1 и 4 — один
источник → одно событие). Флаги: `--no-ring`, `--ring-gain-db` (10),
`--ring-tonality` (8), `--ring-start-windows` (3), `--ring-end-silence`
(1.0), `--ring-warmup` (5), `--ring-max` (180). Офлайн-проверка по
дампу: `./ring_check.py tyk.pcap`.

**Прогрев и страховка (наблюдение 31.10)**: на старте сессии
аудиотракт даёт интермиттящую транзиентку (450 Гц/+18.6 дБ — ложный
ring start; end не пришёл — аудио замолчало; на следующем рестарте не
повторилось). Поэтому: `--ring-warmup N` — первые N секунд аудио
сессии детектор учит базлайн, НЕ стреляя (rearm на каждом реконнекте);
`--ring-max N` — если звонок активен дольше N секунд (аудио замолчало,
end не придёт) — принудительный end с `"stuck": true` (watchdog в
_reaper). Диагностика живых мик: `audio_bytes` по каналам в `/status`.

Валидация: tyk.pcap → start t≈5.7, end t≈10.8; nop.pcap → 0 событий
(все 4 канала). Синтетика (itest8): фон/шум/речь/короткий тон → 0
ложных; рингтон → ровно один start+end; тон на прогреве → 0, после
прогрева → ловится; rearm гасит снова; принудительный end с stuck.

Известное ограничение: громкий тон у панели (клаксон, свист) длиной
>300 мс тоже даст событие — семантически это «громкий звук у двери».

## Громкость локального динамика (TLV 1054/1055) — НЕ ПОДДЕРЖИВАЕТСЯ прошивкой STM83xx

Путь в приложении: кнопки громкости на экране звонка (MainActivity
`btn_device_voice_add/des`) → `_GLNK_V_VolumeConfigRequest(action,
volume=10)` → стрим-сессия.

**НАБЛЮДЕНИЕ 31.10 (железо): TLV 1054 в стрим-сессии прошивка НЕ
поддерживает — закрывает соединение без ответа** (сессия 1269 с умерла
в секунду команды; замок TLV 425 при этом сессию не ронял и отвечал
426). В приложении кнопок громкости на этой панели нет — фича недоступна
и в нём. Тот же паттерн, что у TLV 1007 и 465: неизвестный клиентский
TLV → разрыв соединения.

### TLV 1054 — VolumeConfigRequest (8 байт)

| поле | размер | значение |
|------|--------|----------|
| action | u8 | 1 = громче, 0 = тише |
| volume | u8 | шаг, приложение всегда шлёт 10 |
| reserve | 6 | нули |

### TLV 1055 — VolumeConfigResponse (4 байта)

`result` u16 LE (1 = успех), `reserve` u16. Оба TLV — GLNK-расширение
(goolink), в Command.java `GLNK_T_VOLUMECONFIG_REQ = 1054`.

### В шлюзе

- Эндпоинты и CLI ОСТАВЛЕНЫ (диагностика/другие прошивки платформы),
  но на STM83xx каждый вызов роняет стрим-сессию канала (авто-реконнект
  ~3 с): `POST /volume?ch=1&dir=down&steps=3`, `GET /mute`.
- MQTT: `{base}/cmd/volume {"channel":1,"direction":"down","steps":3}`
  → ack в `{base}/events/volume`.
- `--mute-local N` на этой прошивке НЕ ВКЛЮЧАТЬ: роняет сессию после
  КАЖДОГО логина (по умолчанию 0 — выключен).

## Синхронизация времени (TLV 1007/1008) — реализовано

Путь в приложении: `DeviceRemoteSettingActivity.configTimeSync()` →
`DeviceConfig.configTimeSync(zone, dateTime)` →
`EyeProtocolPacker.createTimeSyncRequestPack`. Приложение шлёт ЛОКАЛЬНОЕ
время телефона + его зону. Для старых прошивок (< 5.0) есть второй
формат (`_TLV_V_TIMESYNREQ`: istwelve/zone/sec/usec, эпоха) — не
реализуем, наша прошивка 5.0.

### TLV 1007 — TimeSyncRequest (32 байта, все u32 LE)

| поле | значение |
|------|----------|
| zone | смещение часового пояса в **МИНУТАХ** (UTC+3 → 180) |
| m_microsecond | на деле **миллисекунды** (`currentTimeMillis()%1000`) |
| m_year / m_month (1-based) / m_day / m_hour / m_minute / m_second | локальное время |

### TLV 1008 — TimeSyncResponse (8 байт)

`result` u16 LE (1 = успех) + reserve[6]... по десериализатору
`TLV_T_TIMESYNRSP`: result u16 + 3×reserve u16.

### В шлюзе

- **Только settings-соединение** (как в приложении), вариант-палитра
  из двух путей APK (оба: streamMode=3, channelMask=1, deviceId=0,
  flag=2, код 5 — ретраи с паузой 5 с):
  - **A (DeviceConfig)**: dataType=0, логин packet_seq=2 → ждать
    result=1 → TLV 1007 с packet_seq=1 (команда собирается до логина,
    m_sequence=1 — как configReboot);
  - **B (GooLinkAdd.sendTimeAsyncCmd)**: dataType=2 OWSP_MIXED_DATA,
    логин packet_seq=1 и TLV 1007 с packet_seq=1 — СРАЗУ за логином,
    НЕ дожидаясь ответа (m_sequence не инкрементится логином).
- **Диагностика**: TLV **1006 (TLV_T_NOTRECOGNIZE)** — прямой ответ
  прошивки «команда не распознана»; логируются все TLV после логина.
- **ВЕРДИКТ (железо 31.10 12:34, окончательный)**: оба варианта — логин
  принимается (result=1, и dt=0, и dt=2), соединение закрывается БЕЗ
  1008 и БЕЗ 1006. Сетевая синхронизация времени прошивкой STM83xx
  НЕ поддерживается (как TLV 465/1054). `--sync-time-every` из
  продюнита убрать; `--sync-time`/`POST /sync-time` остаются как
  диагностика (код 3 + подробный отчёт по вариантам).
- CLI one-shot: `./slinex_rtsp.py --host ... --sync-time`
  (выход 0/2/3/4: ок / логин отклонён / 1007 не принят / сеть).
- HTTP работающего шлюза: `POST /sync-time` → `{"ok": true, ...}`.
- Периодическая: `--sync-time-every H` часов (первая через ~30 с
  после старта). Пока оба варианта не подтверждают работу —
  периодическую из продюнита убрать.
- Событие `timesync` → лог + `/events` + MQTT.

## Монитор небазовых TLV — реализовано

Регистрирует на входе ВСЕ TLV, не являющиеся базовыми для передачи
потоков: событие «tlv» на каждое вхождение (тип, длина, hex-превью 32
байта, канал) → лог + `/events` + MQTT. Повторы в пределах 1 с
коалесируются (поле `count`).

Подавляются (имеют собственную обработку/события):
- хендшейк: 39/40/41/42, keepalive 49, инфо 70/71
- медиа: 97/98/99/100/101, формат: 199/200/203
- ответы на наши команды: 426 (замок), 1055 (громкость), 1008 (время)

Всё прочее — потенциальные спонтанные события прошивки (например,
MD-аларм TLV 341/342 — детектор движения, если прошивка шлёт его в
стрим-сессию): наблюдать `slinex/door/events/tlv` в MQTT.

## MQTT-мост (paho-mqtt, конфиг в файле) — реализовано

Конфиг — INI-файл `slinex_gateway.conf` рядом со скриптом (или
`--config FILE`); секция `[mqtt]`: `enabled`, `host`, `port`,
`username`/`password` (пустые = анонимно; вписываются при включении
авторизации в mosquitto), `client_id`, `base_topic`, `topic_events`,
`topic_commands`, `keepalive`. `--no-mqtt` выключает принудительно.
Клиент paho (совместим с API 1.x/2.x), `connect_async` — сам
переподключается, пока брокер недоступен.

Публикация (QoS 0), JSON:
- `{base}/{events}/ring` — start/end (channels, freq, gain_db,
  duration_s)
- `{base}/{events}/unlock`, `{base}/{events}/volume` — результаты команд
- `{base}/status` — LWT: «offline» при обрыве шлюза, «online» онлайн

Подписка (QoS 0), исполняются рабочим потоком (не сетевым потоком paho):
- `{base}/{cmd}/unlock` `{"channel":1,"action":1,"delay":1[,"pwd":..]}`
- `{base}/{cmd}/volume` `{"channel":1,"direction":"down","steps":3}`

Все события шины (замок/звонок/громкость/неизвестные TLV) публикуются
автоматически — команда, пришедшая по MQTT, получает ack там же.
